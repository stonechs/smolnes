# V3.3 音频时钟静态检查

- 日期：2026-11-21
- 检查对象：`dist/V3.3/final/source/`
- 方式：只读源码检查与常数推算；没有运行程序或修改运行时代码。

## 结论

发现一个明确的名义时钟不匹配：帧调度按 60.0 帧/秒运行，而 APU、DMC 事件与音频采样换算使用 1,789,773 CPU 周期/秒及 262×341 PPU 点/帧，对应约 60.09849 帧/秒。模拟 CPU/APU 时间因此比 48 kHz 音频时间慢约 0.1639%。

这会逐步消耗 DMC 事件调度使用的固定 60 ms 前置量：两种时钟相差约 1.64 ms/实际秒，30 秒累积 49.16 ms，约 36.61 秒累积 60 ms。之后，写入事件的时间戳可能早于音频渲染游标；`audio_render_frames` 的 `while` 会在同一个样本中连续应用所有过期事件，从而压缩/合并 DMC DAC 的变化时刻。这个时序机制与用户报告约半分钟后声音改变的时间相符，是当前比 WinMM 欠载更值得怀疑的代码路径；它本身还不能证明“整体音量变小”的听感原因。

## 计算依据

- 双帧定时器在 `initialize_frame_timers` 中设置 16 ms 和 50 ms 周期；`wait_for_next_frame` 每两帧等待一次 16 ms，第三帧同步到 50 ms 边界。因此名义上 3 帧/50 ms，即 60.0 帧/秒。
- CPU 每帧对应 262×341÷3 = 29,780.6667 个 CPU 周期。使用 1,789,773 周期/秒，得到 60.0984867 帧/秒。
- 相对差约为 0.1638755%；按 60.0 fps 运行时，30 秒的 APU 时间落后约 49.16 ms，36.61 秒落后约 60 ms。
- 音频按 48 kHz 生成，每块 480 帧、共 6 块；DMC 的固定前置量也正是 60 ms。`audio_dmc_event` 将事件周期加上该前置量，渲染器则每个音频样本按 `1,789,773 / 48,000` 推进 DMC 周期。

## 其他路径

- CPU 指令的最低 2 周期由 `apu_clock(cycles + 2)` 补上，PPU 用 `cycles * 3 + 6` 补同一组基础周期；这部分目前彼此一致。
- 音频块内的 DMC 分数周期保存在 `audio_dmc_cycle_fraction`，每样本累加后只留下小数余数，没有发现按样本取整导致的持续累计漂移。
- WinMM 回调与 CPU/APU 都在窗口消息线程运行；最新用户捕获在变小声前后看到每次回填前至少 4/6 个 `WAVEHDR` 仍为 `WHDR_INQUEUE`，回填后至少 5/6 个，`waveOutWrite` 错误为 0，回调最大间隔 31 ms。现有记录不支持缓冲队列耗尽。
- 混音器没有全局按时间递减的音量变量：脉冲/三角/噪声增益按 APU 目标渐变到位，DMC 使用固定 0.50 系数；因此未发现直接的“运行一段时间就逐渐降音量”代码。

## 建议

用户选择保留当前 60 fps 帧调度，并按帧率推导音频侧 CPU 时钟：`60 × 89,342 / 3 = 1,786,840` 周期/秒。独立实验版已按这个时钟生成 APU 音调并推进 DMC PCM 游标；DMC 事件保留 APU 周期/电平，去除固定 60 ms 事件偏移，让六个 WinMM 缓冲自然形成播放延迟。实验版已构建，尚未由用户实际听测；操作路径和结果见 `dist/experiments/v3.3-frame-clock-synced-audio/README.md`。
